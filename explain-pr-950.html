PR #950: Stripe Clock Regression for Interval Switches

Background: The BONA-1885 Incident

In PR #948, we fixed a subtle bug in extractSubscriptionData.ts. When a user switched intervals (e.g., Monthly → Annual) on the same plan, the billing cycle failed to reset. The app would keep billing against the old period, eventually hitting quota limits prematurely.

This happened because Stripe produces a specific invoice shape for "always_invoice" switches: two lines for the same product. The first line is a proration credit (negative), and the second is the new charge (positive).

The old code used lines.find(product), which picked the credit line. Since that credit represented the "unused" portion of the old period, its period.end was in the past, causing the app to ignore the invoice for cycle-reset purposes.

The Intuition: Real Stripe Evidence

We fixed this by prioritizing non-proration lines. However, we didn't have a test suite driving real Stripe test clocks to prove this "dual-line same-product" shape actually exists in the wild. PR #950 closes that gap.

This PR adds tests to the @stripe-clock suite that perform real switches and assert on the resulting invoice structure and DB state.

Code Walkthrough

1. Pinning the Invoice Shape

In fetchPaidSwitchInvoice, we verify exactly what production sees:

expect(invoice.lines.data.length).toBe(2);
// Both lines must be the same product
for (const line of invoice.lines.data) {
  expect(line.pricing?.price_details?.product).toBe(productId);
}
// Exactly one is a proration (the credit)
const credit = invoice.lines.data.find(isProrationLine);
expect(credit.amount).toBeLessThan(0);
// The other is the actual charge
const charge = invoice.lines.data.find((l) => l.id !== credit.id);
expect(charge.amount).toBeGreaterThan(0);

2. Testing Both Directions

The PR tests both Monthly → Annual and Annual → Monthly. This is critical because they fail for different reasons if the logic is wrong:

  • Monthly → Annual: The credit ends before the charge. A "first-match" rule (the old bug) picks the credit and stays pinned to the past.
  • Annual → Monthly: The credit ends after the charge (it was a year-long credit!). A "pick latest period.end" rule would pick the credit, staying pinned to the future.

Self-Check Quiz

1. Why is always_invoice the premise of this regression?

It forces Stripe to generate a proration credit and a new charge on a single invoice.
It prevents Stripe from creating an invoice until the next renewal.

2. Why would a "pick latest period.end" rule fail for Annual → Monthly switches?

The monthly charge ends a year from now.
The annual credit's end date is ~11 months past the new monthly charge's end.
